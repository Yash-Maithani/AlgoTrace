How complexity works

Every algorithm on this site reports a Big O figure and a counted number of comparisons, and the two rarely match. This page explains what each one means, where they come from, and why the disagreement is not a mistake.

What Big O is

Big O answers one question: when the input gets bigger, how much more work does this algorithm do? Not how many seconds it takes, which depends on the machine, and not how many steps exactly, which depends on the input. Just the shape of the growth.

Searching a list of 1,000 names by reading them one at a time takes about ten times the work of searching 100. Double the list, double the work. That relationship is what O(n) says, and it stays true whether the computer is fast or slow.

Because only the shape matters, constants and smaller terms are dropped. An algorithm that does 3n + 50 steps is O(n): at a large enough n the 3 and the 50 stop mattering next to the n. This is why a Big O figure can never tell you which of two O(n) algorithms is faster in practice. It is a statement about scaling, not about speed.

Counting steps from code

You do not guess a Big O figure, you read it off the loops. Here is the inner loop of the bubble sort in sorting_algorithms/bubble_sort.py: 

for i in range(n):
    for j in range(0, n-i-1):
        if arr[j] > arr[j+1]:
            arr[j], arr[j+1] = arr[j+1], arr[j]

Work from the inside out. The comparison on the third line happens once per turn of the inner loop. The inner loop runs n-i-1 times. The outer loop runs n times, with i climbing each time, so the inner loop runs n-1 times, then n-2, then n-3, down to zero.

Ten comparisons, which is 4 + 3 + 2 + 1. That sum has a closed form, n(n-1)/2, and for n = 5 it gives 10. Multiply out and you get (n squared minus n) / 2. Drop the constant and the smaller term and what is left is n squared. Bubble sort is O(n squared), and you arrived at it by counting, not by recognising it.

A rule of thumb that follows from this: one loop over the input is usually O(n), a loop inside a loop is usually O(n squared), and halving the problem each time is usually O(log n). The exceptions are worth checking by counting.

Best, average and worst

The same algorithm can do very different amounts of work on different inputs of the same size, so a single figure is not enough. Insertion sort, in sorting_algorithms/insertion_sort.py, shows all three cases on the same five values:

Insertion sort, five values, counted by running it
InputComparisonsCase
[1, 3, 5, 8, 9]4Best. Every value is already in place, so the inner loop breaks after one look.
[5, 3, 8, 1, 9]6A typical shuffle, which is what the average case describes.
[9, 8, 5, 3, 1]10Worst. Every value has to walk past the whole sorted run.

So insertion sort is O(n) at best and O(n squared) at worst. Both are true, and quoting only one of them is how people end up surprised.

The worst case is usually the one that matters, because it is the promise: it will never be slower than this. The best case is often a trap. Bubble sort is quoted at O(n) in the best case in most textbooks, but the one on this site has no early exit, so it makes the same 10 comparisons on all three inputs above. Its best case really is O(n squared). The figure describes the code you have, not the code the textbook has.

Three notations

Cases and notations are two separate ideas, and mixing them up is the most common mistake in this subject. A case is a kind of input: the best one, a typical one, the worst one. A notation is a claim about how fast a function grows. Any case can be described with any of the three.

OBig O the upper bound
"Grows no faster than." The work stays at or below some constant times this curve once the input is big enough. It is a ceiling, and a ceiling can sit well above the real thing: a linear algorithm is also O(n²)Big O of n squared, which is true and not very useful.
ΩOmega the lower bound
"Grows at least as fast as." The work stays at or above some constant times this curve once the input is big enough. It is a floor.
ΘTheta the tight bound
Both at once: a ceiling and a floor with the same shape, so the growth is pinned down from above and below. Saying Θ(n²)Theta of n squared is the strongest of the three claims.

Bubble sort on this site has no early exit, so it makes n(n-1)/2 comparisons on every input. Its best, average and worst cases are all Θ(n²)Theta of n squared, and the overall ceiling and floor meet there too. Insertion sort's best case is Θ(n)Theta of n and its worst case is Θ(n²)Theta of n squared, so across all inputs the most you can promise is a ceiling of O(n²)Big O of n squared and a floor of Ω(n)Omega of n. No single function is both, so there is no overall ΘTheta. Linear search is the same story: one comparison if the target is first, n if it is last or missing.

A tempting shortcut, and why it is wrong. You will see "O is the worst case, Omega is the best case, Theta is the average." Do not learn it. Those are two different ideas. Insertion sort's best case, a sorted list, costs n-1 comparisons, and that one case has all three bounds of its own: it is O(n)Big O of n, Ω(n)Omega of n and Θ(n)Theta of n. Bubble sort's average case is Θ(n²)Theta of n squared, and so is its worst. Every case has an upper, a lower and a tight bound of its own; best, average and worst are just three of the inputs you can ask about.

What "tight" means, with sliders

A function f is Θ(g)Theta of g when two constants c1 and c2 and a starting size n0 exist so that, for every n from n0 on, c1 × g(n) ≤ f(n) ≤ c2 × g(n). The upper half of that is OBig O, the lower half is ΩOmega. Pick an f and a g, then move the sliders until the blue curve stays between the other two from n0 on. The five curves

Almost everything you meet is one of these five.

O(1) constant
The work does not grow at all. Reading arr[mid] costs the same whether the list holds ten values or ten million. On this site: looking up one array cell, and the best case of binary search when the target is the first middle it tries.
O(log n) logarithmic
Each step throws away a fixed share of what is left, usually half, so the input has to double before the work goes up by one step. On this site: binary search. On 1,024 sorted values it rules out a missing target in 10 comparisons. Linear search needs all 1,024. Jump search sits between the two at O(square root of n): 64 comparisons at worst on the same list.
O(n) linear
One pass over the input. Double the input, double the work. On this site: linear search, which checks every value before it can report that one is missing. Also counting and radix sort: their figures are O(n + k) and O(d(n + b)), and here k, d and b are fixed (99, 2 and 10), so the work grows in a straight line with n.
O(n log n) linearithmic
A linear amount of work, repeated once per halving. This is the best any sort can do when it works by comparing pairs. Counting and radix sort beat it only because they never compare: they need whole numbers in a known range instead. On this site: merge sort and heap sort, in every case.
O(n squared) quadratic
Every element is measured against every other. Fine at n = 10, painful at n = 10,000. On this site: bubble, selection and insertion sort, and Dijkstra, whose implementation here scans every unvisited node to find the nearest.

On a straight axis a large n flattens the four slower curves onto the floor, which is true but hides the comparison. A log axis keeps all five readable.

At n = 10 the gap between O(n log n) and O(n squared) is small enough to ignore. At n = 100 it is a factor of 15. That is the whole argument for caring about complexity: the choice only starts to matter once the input is big, and by then it matters a great deal.

The formula against the counter

Every workspace shows a counter: the exact number of comparisons that run made. The Complexity tab shows a Big O figure. They are answering different questions, so they do not match, and they are not supposed to.

The counter matches the exact formula every time, because that is what the code does. It is about half of n squared, and it stays about half however large n gets. That constant factor of two is exactly what Big O throws away.

So read them as a pair. The counter tells you what this run cost. Big O tells you what the next, larger run will cost relative to this one. If you need to compare two algorithms on the input you actually have, the counter is the honest answer. If you need to know which one survives a hundred times more data, Big O is.

Auxiliary space

The same idea applies to memory. Auxiliary space is the memory an algorithm needs on top of the input it was given. The input itself does not count, because you had to store it either way.

Bubble sort needs two loop counters and one temporary during a swap. That is three values whether the list holds ten numbers or ten million, so its auxiliary space is O(1). Merge sort builds a temporary list while merging, and that list grows with the input, so its auxiliary space is O(n).

The case people miss: the recursion stack

Memory is not only what you allocate. Every pending function call occupies a frame on the call stack, and those frames add up. The heap sort here, in sorting_algorithms/heap_sort.py, repairs the heap with a function that calls itself: 

def heapify(arr, n, i):
    ...
    if largest != i:
        arr[i], arr[largest] = arr[largest], arr[i]
        heapify(arr, n, largest)

It sorts inside the original array and allocates nothing, which is why heap sort is usually quoted at O(1) space. But each call waits for the one below it to return, and the chain is as deep as the heap is tall, which is log n. So the honest figure for this heap sort is O(log n). Rewriting heapify as a loop would make it O(1) without changing a single comparison.

Quick sort has the same story with a worse ending. It allocates nothing either, but it always picks the last element as its pivot, so on an already sorted list every partition peels off one value and the recursion nests n deep. Its space here is O(n), not the O(log n) usually quoted.

This is the point of deriving the figures from the code rather than copying them: three of the figures on this site differ from the textbook, and in every case the code is what decides.
